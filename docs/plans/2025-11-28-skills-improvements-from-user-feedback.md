# 基于用户反馈的技能改进

**日期：** 2025-11-28
**状态：** 草案
**来源：** 两个在实际开发场景中使用 superpowers 的 Claude 实例

---

## 执行摘要

两个 Claude 实例从实际开发会话中提供了详细反馈。他们的反馈揭示了当前技能中的**系统性差距**，即使遵循技能也允许可预防的 bug 被发布。

**关键洞察：** 这些是问题报告，不仅仅是解决方案提案。问题是真实的；解决方案需要仔细评估。

**关键主题：**
1. **验证差距** - 我们验证操作成功但不验证它们实现了预期结果
2. **流程卫生** - 后台进程累积并在 subagent 之间干扰
3. **上下文优化** - Subagent 获得太多无关信息
4. **自我反思缺失** - 交接前没有批判自己工作的提示
5. **Mock 安全性** - Mock 可能在没有检测的情况下偏离接口
6. **技能激活** - 技能存在但未被阅读/使用

---

## 识别的问题

### 问题 1：配置变更验证差距

**发生的情况：**
- Subagent 测试了 "OpenAI 集成"
- 设置了 `OPENAI_API_KEY` 环境变量
- 获得了状态 200 响应
- 报告 "OpenAI 集成工作正常"
- **但是** 响应包含 `"model": "claude-sonnet-4-20250514"` - 实际上在使用 Anthropic

**根本原因：**
`verification-before-completion` 检查操作成功但不检查结果反映预期的配置变更。

**影响：** 高 - 集成测试中的虚假信心，bug 被发布到生产环境

**示例失败模式：**
- 切换 LLM 提供商 → 验证状态 200 但不检查模型名称
- 启用功能开关 → 验证没有错误但不检查功能是否激活
- 更改环境 → 验证部署成功但不检查环境变量

---

### 问题 2：后台进程累积

**发生的情况：**
- 会话期间派出了多个 subagent
- 每个都启动了后台服务器进程
- 进程累积（4+ 个服务器运行）
- 陈旧进程仍然绑定端口
- 后来的 E2E 测试命中了配置错误的陈旧服务器
- 令人困惑/错误的测试结果

**根本原因：**
Subagent 是无状态的 - 不知道之前 subagent 的进程。没有清理协议。

**影响：** 中高 - 测试命中错误的服务器，虚假通过/失败，调试困惑

---

### 问题 3：Subagent 提示中的上下文膨胀

**发生的情况：**
- 标准方法：给 subagent 完整的计划文件阅读
- 实验：只给任务 + 模式 + 文件 + 验证命令
- 结果：更快、更专注、单次尝试完成更常见

**根本原因：**
Subagent 在无关计划部分浪费 token 和注意力。

**影响：** 中 - 执行更慢，更多失败尝试

**有效的方法：**
```
你正在向 packnplay 的测试套件添加单个 E2E 测试。

**你的任务：** 将 `TestE2E_FeaturePrivilegedMode` 添加到 `pkg/runner/e2e_test.go`

**测试内容：** 在其元数据中请求 `"privileged": true` 的本地 devcontainer feature 应该导致容器以 `--privileged` 标志运行。

**遵循 TestE2E_FeatureOptionValidation 的确切模式**（在文件末尾）

**编写后运行：** `go test -v ./pkg/runner -run TestE2E_FeaturePrivilegedMode -timeout 5m`
```

### 问题 4：交接前没有自我反思

**发生的情况：**
- 添加了自我反思提示："用新鲜的眼光看你的工作 - 有什么可以更好？"
- 任务 5 的实现者识别出失败的测试是由于实现 bug，而不是测试 bug
- 追踪到第 99 行：`strings.Join(metadata.Entrypoint, " ")` 创建了无效的 Docker 语法
- 没有自我反思，只会报告 "测试失败" 而没有根本原因

**根本原因：**
实现者在报告完成前不会自然地退一步批判自己的工作。

**影响：** 中 - 实现者可以捕获的 bug 被移交给审查者

---

### 问题 5：Mock-接口 偏移

**发生的情况：**
```typescript
// 接口定义 close()
interface PlatformAdapter {
  close(): Promise<void>;
}

// 代码（有 bug）调用 cleanup()
await adapter.cleanup();

// Mock（匹配 bug）定义 cleanup()
vi.mock('web-adapter', () => ({
  WebAdapter: vi.fn().mockImplementation(() => ({
    cleanup: vi.fn().mockResolvedValue(undefined),  // 错误！
  })),
}));
```
- 测试通过
- 运行时崩溃："adapter.cleanup is not a function"

**根本原因：**
Mock 派生自有 bug 的代码调用，而不是接口定义。TypeScript 无法捕获内联 mock 中的错误方法名。

**影响：** 高 - 测试给出虚假信心，运行时崩溃

**为什么 testing-anti-patterns 没有阻止这个：**
该技能涵盖测试 mock 行为和在不理解的情况下 mock，但没有特定的模式"从接口派生 mock，而不是实现。"

---

### 问题 6：代码审查者文件访问

**发生的情况：**
- 派出了代码审查 subagent
- 找不到测试文件："该文件在仓库中不存在"
- 文件实际上存在
- 审查者不知道要先显式读取它

**根本原因：**
审查者提示不包括显式文件读取指令。

**影响：** 低中 - 审查失败或不完整

---

### 问题 7：修复工作流延迟

**发生的情况：**
- 实现者在自我反思期间识别 bug
- 实现者知道修复方法
- 当前工作流：报告 → 我派出修复者 → 修复者修复 → 我验证
- 额外往返增加延迟而不增加价值

**根本原因：**
当实现者已经诊断时，实现者和修复者角色之间的严格分离。

**影响：** 低 - 延迟，但没有正确性问题

---

### 问题 8：技能未被阅读

**发生的情况：**
- `testing-anti-patterns` 技能存在
- 人类和 subagent 在编写测试前都没有阅读它
- 本可以防止一些问题（尽管不是全部 - 见问题 5）

**根本原因：**
没有强制 subagent 阅读相关技能。没有提示包含技能阅读。

**影响：** 中 - 如果不使用，技能投资就浪费了

## 建议的改进

### 1. verification-before-completion：添加配置变更验证

**添加新部分：**

```markdown
## 验证配置变更

当测试配置、提供商、功能开关或环境的变更时：

**不要只验证操作成功。验证输出反映预期的变更。**

### 常见失败模式

操作成功是因为存在*某些*有效配置，但它不是你打算测试的配置。

### 示例

| 变更 | 不充分 | 必需 |
|--------|-------------|----------|
| 切换 LLM 提供商 | 状态 200 | 响应包含预期的模型名称 |
| 启用功能开关 | 没有错误 | 功能行为实际激活 |
| 更改环境 | 部署成功 | 日志/变量引用新环境 |
| 设置凭据 | 认证成功 | 认证用户/上下文正确 |

### 关口函数

```
在声称配置变更工作之前：

1. 识别：此变更后有什么应该不同？
2. 定位：那个差异在哪里可观察？
   - 响应字段（模型名称、用户 ID）
   - 日志行（环境、提供商）
   - 行为（功能激活/未激活）
3. 运行：显示可观察差异的命令
4. 验证：输出包含预期差异
5. 只有然后：声称配置变更工作

红旗：
  - "请求成功" 而不检查内容
  - 检查状态码但不检查响应体
  - 验证没有错误但没有正面确认
```

**为什么这有效：**
强制验证意图，不仅仅是操作成功。

### 2. subagent-driven-development：为 E2E 测试添加流程卫生

**添加新部分：**

```markdown
## E2E 测试的流程卫生

当派遗启动服务（服务器、数据库、消息队列）的 subagent 时：

### 问题

Subagent 是无状态的 - 它们不知道之前 subagent 启动的进程。后台进程持续存在并可能干扰后续测试。

### 解决方案

**在派遗 E2E 测试 subagent 之前，在提示中包含清理：**

```
在启动任何服务之前：
1. 终止现有进程：pkill -f "<service-pattern>" 2>/dev/null || true
2. 等待清理：sleep 1
3. 验证端口空闲：lsof -i :<port> && echo "错误：端口仍在使用" || echo "端口空闲"

测试完成后：
1. 终止你启动的进程
2. 验证清理：pgrep -f "<service-pattern>" || echo "清理成功"
```

### 示例

```
任务：运行 API 服务器的 E2E 测试

提示包括：
"在启动服务器之前：
- 终止任何现有服务器：pkill -f 'node.*server.js' 2>/dev/null || true
- 验证端口 3001 空闲：lsof -i :3001 && exit 1 || echo '端口可用'

测试后：
- 终止你启动的服务器
- 验证：pgrep -f 'node.*server.js' || echo '清理已验证'"
```

### 为什么这很重要

- 陈旧进程以错误配置提供请求
- 端口冲突导致静默失败
- 进程累积减慢系统
- 令人困惑的测试结果（命中错误的服务器）
```

**权衡分析：**
- 向提示添加样板
- 但防止非常令人困惑的调试
- 对 E2E 测试 subagent 值得

### 3. subagent-driven-development：添加精简上下文选项

**修改步骤 2：使用 Subagent 执行任务**

**之前：**
```
从 [plan-file] 仔细阅读该任务。
```

**之后：**
```
## 上下文方法

**完整计划（默认）：**
当任务复杂或有依赖关系时使用：
```
从 [plan-file] 仔细阅读任务 N。
```

**精简上下文（用于独立任务）：**
当任务是独立的和基于模式时使用：
```
你正在实现：[1-2 句任务描述]

要修改的文件：[确切路径]
要遵循的模式：[对现有函数/测试的引用]
要实现什么：[具体要求]
验证：[要运行的确切命令]

[不要包含完整计划文件]
```

**何时使用精简上下文：**
- 任务遵循现有模式（添加类似测试、实现类似功能）
- 任务是自包含的（不需要其他任务的上下文）
- 模式引用足够（例如，"遵循 TestE2E_FeatureOptionValidation"）

**何时使用完整计划：**
- 任务依赖于其他任务
- 需要理解整体架构
- 需要上下文的复杂逻辑
```

**示例：**
```
精简上下文提示：

"你正在为 devcontainer 功能中的特权模式添加测试。

文件：pkg/runner/e2e_test.go
模式：遵循 TestE2E_FeatureOptionValidation（在文件末尾）
测试：元数据中有 `"privileged": true` 的功能导致 `--privileged` 标志
验证：go test -v ./pkg/runner -run TestE2E_FeaturePrivilegedMode -timeout 5m

报告：实现、测试结果、任何问题。"
```

**为什么这有效：**
减少 token 使用，增加专注，适当时更快完成。

### 6. testing-anti-patterns：添加 Mock-接口偏移反模式

**添加新反模式 6：**

```markdown
## 反模式 6：从实现派生的 Mock

**违规：**
```typescript
// 代码（有 bug）调用 cleanup()
await adapter.cleanup();

// Mock（匹配 bug）有 cleanup()
const mock = {
  cleanup: vi.fn().mockResolvedValue(undefined)
};

// 接口（正确）定义 close()
interface PlatformAdapter {
  close(): Promise<void>;
}
```

**为什么这是错的：**
- Mock 将 bug 编码到测试中
- TypeScript 无法捕获方法名错误的内联 mock
- 测试通过因为代码和 mock 都是错的
- 使用真实对象时运行时崩溃

**修复：**
```typescript
// ✅ 好：从接口派生 mock

// 步骤 1：打开接口定义（PlatformAdapter）
// 步骤 2：列出那里定义的方法（close、initialize 等）
// 步骤 3：Mock 确切地那些方法

const mock = {
  initialize: vi.fn().mockResolvedValue(undefined),
  close: vi.fn().mockResolvedValue(undefined),  // 来自接口！
};

// 现在测试失败因为代码调用不存在的 cleanup()
// 那个失败在运行时之前揭示了 bug
```

### 关口函数

```
在编写任何 mock 之前：

  1. 停止 - 还不要看被测代码
  2. 查找：依赖的接口/类型定义
  3. 阅读：接口文件
  4. 列出：接口中定义的方法
  5. Mock：只有那些方法，确切地那些名称
  6. 不要：看你的代码调用什么

  如果你的测试失败因为代码调用 mock 中没有的东西：
    ✅ 好 - 测试发现了你代码中的 bug
    修复代码以调用正确的接口方法
    不是 mock

  红旗：
    - "我会 mock 代码调用的内容"
    - 从实现复制方法名
    - 没有阅读接口就编写 mock
    - "测试失败所以我会在 mock 中添加这个方法"
```

**检测：**

当你看到运行时错误 "X is not a function" 且测试通过：
1. 检查 X 是否被 mock
2. 比较 mock 方法与接口方法
3. 查找方法名不匹配
```

**为什么这有效：**
直接解决反馈中的失败模式。

### 8. subagent-driven-development：允许实现者修复自己识别的问题

**修改步骤 2：**

**当前：**
```
Subagent 带工作摘要报告回来。
```

**建议：**
```
Subagent 执行自我反思，然后：

如果自我反思识别出可修复的问题：
  1. 修复问题
  2. 重新运行验证
  3. 报告："初始实现 + 自我反思修复"

否则：
  报告："实现完成"

在报告中包括：
- 自我反思发现
- 是否应用了修复
- 最终验证结果
```

**为什么这有效：**
当实现者已经知道修复时减少延迟。文档记录的案例：本可以节省入口点 bug 的一次往返。

**权衡：**
提示稍复杂，但端到端更快。

1. **精简上下文方法：**

   - 我们如何决定使用哪种方法？
   - 太精简并错过重要上下文的风险？

   - 这会显著减慢简单任务吗？
   - 应该只适用于复杂任务吗？
   - 我们如何防止"反思疲劳"变成机械的？

   - 这应该在 subagent-driven-development 还是单独的技能中？

   - 我们如何处理进程应该持久的情况（开发服务器）？

4. **技能阅读强制：**
   - 我们应该要求所有 subagent 阅读相关技能吗？
   - 我们如何防止提示变得太长？
   - 过度文档化和失去焦点的风险？

## 成功指标

我们如何知道这些改进有效？

1. **配置验证：**
   - 零实例的"测试通过但使用了错误配置"
   - Jesse 不会说"那实际上不是在测试你认为的"

2. **流程卫生：**
   - 零实例的"测试命中错误的服务器"
   - E2E 测试运行期间没有端口冲突错误

3. **Mock-接口偏移：**
   - 零实例的"测试通过但运行时因缺少方法崩溃"
   - Mock 和接口之间没有方法名不匹配

4. **自我反思：**
   - 可衡量：实现者报告是否包含自我反思发现？
   - 定性：更少的 bug 进入代码审查吗？

5. **技能阅读：**
   - Subagent 报告引用技能关口函数
   - 代码审查中更少的反模式违规

## 风险和缓解

### 风险：提示膨胀
**问题：** 添加所有这些要求使提示不堪重负
**缓解：**
- 分阶段实现（不要一次添加所有内容）
- 使某些添加有条件（E2E 卫生只用于 E2E 测试）
- 考虑不同任务类型的模板

### 风险：分析瘫痪
**问题：** 太多反思/验证减慢执行
**缓解：**
- 保持关口函数快速（秒，不是分钟）
- 最初让精简上下文选择加入
- 监控任务完成时间

### 风险：虚假安全感
**问题：** 遵循检查清单不保证正确性
**缓解：**
- 强调关口函数是最低要求，不是最高要求
- 在技能中保留"使用判断"语言
- 记录技能捕获常见失败，不是所有失败

### 风险：技能分歧
**问题：** 不同技能给出冲突建议
**缓解：**
- 审查所有技能的更改以确保一致性
- 记录技能如何交互（集成部分）
- 在部署前用真实场景测试
